# Product Spec

## 1. 제품 목적

### 확정

`personal-resume-management`의 1차 목적은 **채용 지원용 PDF 이력서를 쉽게 작성·편집·관리하는 개인용 Resume Builder**를 만드는 것입니다.

단순한 HTML 이력서 파일이 아니라 다음을 지원합니다.

- 이력서 각 섹션 직접 편집
- 항목 추가·삭제
- 항목 순서 변경
- 항목 표시·숨김
- 지원처에 따라 구성과 강조점 변경
- A4 PDF 출력
- 집 PC와 노트북 등 여러 기기에서 같은 이력서 데이터 사용
- 웹에서는 누구나 이력서를 볼 수 있지만 편집은 본인만 가능

### 결정 이유

- 최근 지원처는 대부분 PDF 이력서를 요구함
- 기존 Resume Builder의 편집 UX는 편했지만 기본 템플릿과 정보 구조에는 한계가 있었음
- 쉽게 수정하는 사용성은 유지하면서 이력서 구조와 디자인을 직접 설계하기로 함

---

## 2. 장기 방향

### 확정 방향

현재는 PDF 이력서 제작을 우선합니다.

첫 직장 이후에는 개인 커리어 관리, 경력 소개, 헤드헌팅 등에 활용할 수 있는 **개인 커리어 웹사이트**로 확장할 가능성을 열어둡니다.

다만 현재 단계에서 장기 기능을 미리 과도하게 구현하지 않습니다.

---

## 3. MVP 기능 범위

### 확정

#### 이력서 편집

- 섹션별 내용 직접 편집
- 항목 추가
- 항목 삭제
- 항목 순서 변경
- 항목 표시/숨김
- 지원처에 맞게 일부 구성과 강조 순서를 변경할 수 있는 구조

기존 Resume Builder처럼 **완성된 이력서 화면 자체에서 섹션을 클릭해 편집하고, 바깥 영역을 클릭하면 편집을 종료하면서 자동 저장되는 사용성**을 지향합니다.

자동 저장은 현재 버전의 최신 상태를 갱신하는 동작이며, 자동 저장마다 새 버전을 만들지는 않습니다.

#### 여러 기기에서 사용

- 집 PC와 노트북 등 다른 단말에서도 동일한 데이터를 사용
- `localStorage`만으로 끝내지 않고 클라우드 저장 사용

#### PDF 출력

- 채용 제출용 최우선 결과물은 PDF
- A4 기준 출력
- 페이지 수를 1p/2p/3p로 미리 고정하지 않음

세부 출력 규칙은 [DESIGN_PRINT_SPEC.md](DESIGN_PRINT_SPEC.md)에서 관리합니다.

## 4. 지원처와 이력서 버전 관리

### 확정

이력서는 **지원처를 상위 단위로 두고, 각 지원처 안에서 여러 버전을 관리**합니다.

```text
지원처
├─ 마스터
│  ├─ v1.0
│  └─ v1.1
├─ 네이버웹툰
│  ├─ v1.0
│  └─ v2.0
└─ 시프트업
   └─ v1.0
```

`마스터`가 필요하면 시스템적으로 특별한 개체를 만들지 않고, 이름이 `마스터`인 일반 지원처로 사용합니다. 즉 특정 버전이 다른 버전의 영구 원본이 되거나 자동 동기화되는 구조는 두지 않습니다.

### 새 지원처 / 버전 생성

사용자는 자유롭게 다음 방식 중 하나를 선택할 수 있습니다.

- 빈 이력서로 시작
- 같은 지원처의 기존 버전을 복제
- 다른 지원처의 원하는 버전을 복제

예를 들어 `시프트업 v2.0`을 기반으로 `네이버웹툰 v1.0`을 만들어 수정할 수 있습니다.

어느 버전도 특별한 원본으로 강제하지 않고, 그때그때 가장 적합한 기존 버전을 출발점으로 선택할 수 있게 합니다.

### 버전 번호

버전은 `v{major}.{minor}` 형식을 기본으로 사용합니다.

- **Major**: 방향이나 구성이 크게 달라지는 수정
  - 예: 자기소개 방향 변경, 프로젝트 구성 대폭 변경, 섹션 구조 재설계
- **Minor**: 기존 방향 안에서의 비교적 작은 수정
  - 예: 일부 문구 수정, 프로젝트 일부 교체, 순서 조정, 표현 보완

예:

```text
v1.0 → v1.1 → v1.2 → v2.0
```

새 버전은 사용자가 명시적으로 `새 버전 만들기`를 선택했을 때 생성합니다. 생성 시 Major / Minor 중 하나를 선택하면 번호를 자동 증가시키는 방향으로 설계합니다.

### 버전 메타정보

버전 번호와 시간 정보는 분리합니다.

각 버전은 최소한 다음 메타정보를 가집니다.

- 버전 번호 (`v1.0`, `v1.1`, `v2.0` 등)
- 선택적 라벨 / 설명
- 생성 일시
- 최종 수정 일시
- 복제해 만든 경우 원본 지원처 / 버전 정보

화면에서는 필요에 따라 다음처럼 표시할 수 있습니다.

```text
v1.2 · 자기소개 수정
2026.09.15 생성 · 2026.09.15 수정
```

버전의 라벨은 사용자가 직접 수정할 수 있게 합니다. 예: `v2.0 · 최종 제출본`.

### 자동 저장과 히스토리

자동 저장과 버전 생성은 분리합니다.

- 섹션 편집 후 바깥을 클릭하면 현재 버전에 자동 저장
- 자동 저장만으로 버전 번호는 증가하지 않음
- 현재 버전 안에서는 가벼운 변경 히스토리를 남길 수 있게 함
- 중요한 시점은 사용자가 새 Major / Minor 버전으로 직접 저장

히스토리는 버전 자체를 대체하지 않으며, 잦은 자동 저장 때문에 `v27`, `v28`처럼 불필요한 버전이 생기지 않게 합니다.

## 5. 데이터 구조 요구사항

### 확정된 요구사항

데이터 구조는 최소한 다음 동작을 지원해야 합니다.

- 지원처별 데이터 관리
- 지원처 내부의 여러 이력서 버전 관리
- 빈 이력서에서 새 버전 생성
- 같은 지원처 또는 다른 지원처의 특정 버전 복제
- Major / Minor 버전 번호 관리
- 버전 라벨, 생성 일시, 수정 일시 관리
- 현재 버전의 자동 저장
- 버전별 가벼운 변경 히스토리 관리
- 섹션별 데이터 관리
- 항목 추가/삭제
- 항목 순서 변경
- 표시/숨김
- 여러 기기에서 같은 데이터 사용

### 프로젝트 데이터에서 합의된 개념 필드

- 프로젝트명
- 설명 / 한 줄 정의
- 기간
- 팀 규모
- 역할
- Abstract 1
- Abstract 2
- Abstract 3
- 링크
- 표시 여부

위 항목은 **개념적 편집 필드**이며 실제 DB/API 스키마는 아직 확정하지 않았습니다.

## 6. 사용자 흐름

### 공개 사용자

1. 웹사이트 접속
2. 이력서 열람
3. 웹 형태 또는 PDF 결과 확인

### 편집 사용자

1. 웹사이트 접속
2. 편집 요청
3. 로컬 Authenticator로 Challenge-Response 인증
4. 인증 성공
5. 지원처와 이력서 버전 선택
6. 편집 모드 진입
7. 섹션 클릭 후 내용 수정
8. 바깥 영역 클릭 시 현재 버전에 자동 저장
9. 필요하면 Major / Minor 새 버전 생성
10. 필요하면 다른 지원처의 특정 버전을 복제해 새 지원처 또는 버전 생성
11. PDF 출력
12. 마지막 활동을 기준으로 1시간 동안 편집 세션 유지

인증 세부사항은 [AUTH_SECURITY_SPEC.md](AUTH_SECURITY_SPEC.md)에서 관리합니다.

## 7. 이력서 콘텐츠 원칙

### 확정

- 이력서는 프로젝트·경력의 요약과 면접 질문의 출발점으로 사용
- 상세 문제 해결 과정은 포트폴리오에서 설명
- 프로젝트별 Tools 반복 나열 대신 별도 Skills 섹션 사용
- 지원처별로 프로젝트 순서와 표시 여부를 조정할 수 있게 함

세부 섹션 구조는 [RESUME_STRUCTURE.md](RESUME_STRUCTURE.md)에서 관리합니다.
