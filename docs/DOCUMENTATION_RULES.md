# Documentation Rules

이 문서는 프로젝트 문서를 어떤 기준으로 작성하고 갱신할지 정합니다.

## 1. 문서는 결정의 근거를 남긴다

중요한 선택에는 가능한 범위에서 다음을 함께 기록합니다.

- 어떤 문제가 있었는지
- 어떤 조건을 기준으로 판단했는지
- 무엇을 선택했는지
- 아직 결정하지 않은 것은 무엇인지

새로운 내용을 자연스럽게 보이게 하려고 임의로 채우지 않습니다.

---

## 2. 상태를 구분한다

### 확정

대화, 실제 자료, 구현 결과 등으로 이미 정한 내용입니다.

### 방향

큰 방향은 합의했지만 세부 구현이나 수치가 아직 남은 내용입니다.

### TBD

선택지가 남아 있거나 근거가 부족해 아직 정하지 않은 내용입니다.

확정된 요구사항과 구현 아이디어를 같은 수준으로 쓰지 않습니다.

---

## 3. 문서 구조

### `README.md`

프로젝트에 처음 들어왔을 때 필요한 정보만 둡니다.

- 프로젝트 한 줄 목적
- 현재 확정된 큰 방향
- MVP 요약
- 문서 링크
- 공개 저장소 보안 원칙

### `docs/PRODUCT_SPEC.md`

제품 관점의 기준을 관리합니다.

- 제품 목적
- MVP 기능 범위
- 마스터 데이터와 지원처별 버전
- 데이터 구조 요구사항
- 상위 사용자 흐름
- 미확정 제품/기술 항목

### `docs/RESUME_STRUCTURE.md`

이력서 콘텐츠와 정보 구조를 관리합니다.

- Profile / Header
- Timeline
- Projects
- Experience
- Skills
- Education
- Relevant Training
- Awards / Activities
- Certification / Language
- 지원처별 재구성 원칙

### `docs/DESIGN_PRINT_SPEC.md`

시각적 방향과 PDF 출력 기준을 관리합니다.

- 전체 디자인 원칙
- 타임라인 디자인
- A4 출력
- 페이지 분할 원칙
- 편집 화면과 출력 결과의 관계

### `docs/AUTH_SECURITY_SPEC.md`

인증과 보안 기준을 관리합니다.

- 공개 열람 / 편집 권한
- 로컬 Authenticator
- Challenge-Response
- key pair
- 편집 세션
- 미확정 인증 UX
- 공개 저장소 보안 원칙

### `docs/ARCHITECTURE.md`

현재 확정된 기술 인프라와 미확정 기술 선택을 관리합니다.

- GitHub
- Vercel
- 데이터 저장 요구사항
- 인증 구조 참조
- 아직 결정하지 않은 기술 스택

---

## 4. 문장 작성 기준

- 한 문단에는 가능한 한 하나의 핵심만 둡니다.
- 긴 배경 설명보다 결정과 이유가 먼저 보이게 씁니다.
- 같은 내용을 여러 문서에서 길게 반복하지 않고 기준 문서로 링크합니다.
- 수치·성과·경험은 실제 근거가 있을 때만 적습니다.
- 구현 아이디어를 확정사항처럼 적지 않습니다.
- 결정이 바뀌면 현재 기준과 변경 이유가 드러나도록 갱신합니다.

---

## 5. 공개 저장소에 작성하지 않는 것

- 전화번호, 개인 이메일 등 실제 이력서 개인정보
- private key
- access token / API key
- session secret
- 기타 인증 비밀값
- 공개하면 안 되는 외부 문서 원문

예시 데이터가 필요하면 실제 정보 대신 명백한 더미 데이터를 사용합니다.

---

## 6. 변경 시 원칙

기능이나 기술 방향을 바꿀 때는 관련 문서를 함께 갱신합니다.

예를 들어 인증 방식을 바꾸면 코드만 수정하지 않고 다음을 함께 확인합니다.

1. `AUTH_SECURITY_SPEC.md`의 인증 흐름과 보안 경계
2. `ARCHITECTURE.md`의 기술 구조
3. `PRODUCT_SPEC.md`의 편집 사용자 흐름
4. README의 상위 방향

문서는 구현을 뒤늦게 설명하는 기록이 아니라, 구현 기준을 공유하는 기준 문서로 사용합니다.
