# Documentation Rules

이 문서는 프로젝트 문서를 어떤 기준으로 작성하고 갱신할지 정합니다.

## 1. 문서는 결정의 근거를 남긴다

단순히 `무엇을 쓴다`만 적지 않고, 중요한 선택에는 가능한 범위에서 다음 내용을 함께 남깁니다.

- 어떤 문제가 있었는지
- 어떤 조건을 기준으로 판단했는지
- 무엇을 선택했는지
- 아직 확인하지 못한 것은 무엇인지

결정 과정이 없는 세부 구현 설명은 필요한 문서에서만 다룹니다.

---

## 2. 사실과 추측을 섞지 않는다

모든 핵심 항목은 아래 상태 중 하나로 관리합니다.

### 확정

대화, 실제 자료, 구현 결과 등으로 이미 확인된 내용입니다.

### 가설

현재 설계를 진행하기 위해 임시로 잡은 방향입니다. 구현 전에 다시 확인할 수 있습니다.

### TBD

근거가 부족하거나 선택지가 남아 있어 아직 정하지 않은 내용입니다.

모르는 내용을 자연스럽게 보이게 하려고 임의로 채우지 않습니다.

---

## 3. 문서 구조

### README.md

프로젝트에 처음 들어왔을 때 필요한 정보만 둡니다.

- 프로젝트 목적
- 현재 상태
- 확정된 큰 방향
- 문서 링크
- 저장소 보안 원칙

세부 정책과 설계는 README에 길게 쌓지 않습니다.

### docs/PRODUCT_SPEC.md

제품 관점의 기준을 관리합니다.

- 해결하려는 문제
- 제품 목적
- 관리 단위
- 범위
- 기능 우선순위
- 미결정 항목

### docs/ARCHITECTURE.md

기술 선택과 보안 경계를 관리합니다.

- 배포 구조
- 인증 방식
- 데이터 흐름
- 외부 서비스 의존성
- 보안 원칙
- 기술 미결정 사항

필요해지면 기능별 세부 문서를 `docs/` 아래에 추가합니다.

---

## 4. 문장 작성 기준

- 한 문단에는 가능한 한 하나의 핵심만 둡니다.
- 긴 배경 설명보다 결정과 이유가 먼저 보이게 씁니다.
- 같은 내용을 여러 문서에서 반복하지 않고 기준 문서로 링크합니다.
- 개발 용어는 필요한 경우에만 사용하고, 역할이 드러나도록 씁니다.
- 숫자·성과·경험은 실제 근거가 있을 때만 적습니다.
- 구현이 바뀌면 과거 결정을 지우기보다 현재 기준이 무엇인지 분명하게 갱신합니다.

---

## 5. 공개 저장소에 작성하지 않는 것

- 전화번호, 개인 이메일 등 실제 이력서 개인정보
- 비밀키
- access token / API key
- 인증 secret
- 공개하면 안 되는 외부 문서 원문

예시 데이터가 필요하면 실제 정보 대신 명백한 더미 데이터를 사용합니다.

---

## 6. 변경 시 원칙

기능이나 기술 방향을 바꿀 때는 관련 문서를 함께 갱신합니다.

예를 들어 인증 방식을 바꾸면 코드만 수정하지 않고 `ARCHITECTURE.md`의 다음 내용도 확인합니다.

1. 기존 선택 이유가 여전히 맞는지
2. 무엇이 바뀌었는지
3. 보안 경계가 달라지는지
4. 새로 생긴 TBD가 있는지

문서는 구현을 뒤늦게 설명하는 기록이 아니라, 구현 기준을 공유하는 기준 문서로 사용합니다.
