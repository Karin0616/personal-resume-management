# Architecture

## 1. 현재 확정된 기술 방향

### 배포

- **Vercel 사용**
- Cloudflare는 이 프로젝트의 기본 인프라에서 제외

Cloudflare를 사용할 수 없어서가 아니라, 다른 프로젝트에서 무료 사용 범위를 이미 많이 사용하고 있어 이 프로젝트까지 의존시키지 않는 방향으로 정했습니다.

### 인증

- **공개키 기반 challenge-response 방식 사용**
- 서버에는 인증에 필요한 공개키만 둔다.
- 비밀키는 GitHub 저장소와 Vercel 환경에 저장하지 않는다.

---

## 2. 인증 흐름 초안

아래 흐름은 현재 합의한 challenge-response 방향을 구조화한 것입니다.

```text
Client                          Server
  |                               |
  | ---- challenge 요청 --------> |
  | <--- 일회성 challenge -------- |
  |                               |
  | challenge를 비밀키로 서명      |
  |                               |
  | ---- signature 전송 --------> |
  |                               |
  | 공개키로 signature 검증        |
  | challenge 재사용 여부 확인      |
  |                               |
  | <--- 인증 성공 / 실패 -------- |
```

### 서버가 확인해야 할 것

1. 서버가 직접 발급한 challenge인지
2. 아직 만료되지 않았는지
3. 이미 사용한 challenge가 아닌지
4. 등록된 공개키로 signature 검증이 성공하는지

challenge는 인증마다 새로 발급하고, 성공·실패 여부와 관계없이 재사용할 수 없도록 설계하는 방향을 우선합니다.

---

## 3. 보안 경계

### 확정

공개 저장소에 아래 정보는 커밋하지 않습니다.

- 개인 이력서 원문의 전화번호·이메일 등 개인정보
- 비밀키
- API token
- 세션 secret
- 기타 인증에 사용할 수 있는 비밀값

### 원칙

공개키는 노출되어도 인증 비밀이 되지 않으므로 서버 측 검증 정보로 사용할 수 있습니다.

반대로 비밀키는 사용자의 소유 영역을 벗어나지 않아야 합니다.

---

## 4. 아직 결정하지 않은 부분

다음 항목은 현재 정보만으로 확정하지 않습니다.

### TBD · 비밀키 보관 및 서명 방식

브라우저에서 어떤 방식으로 비밀키를 보관하고 challenge를 서명할지 결정이 필요합니다.

후보 기술을 먼저 정하지 않고 아래 조건으로 비교합니다.

- 비밀키가 서버로 전달되지 않을 것
- 사용자가 매번 과도한 인증 절차를 반복하지 않을 것
- 브라우저 재접속 시 동작 방식이 명확할 것
- 키 분실·교체 시 복구 절차를 정의할 수 있을 것

### TBD · 인증 이후 세션 유지 방식

challenge-response는 본인 확인 단계로 사용하고, 이후 요청을 어떤 방식으로 인증 상태로 유지할지는 별도로 결정합니다.

### TBD · 데이터 저장소

이력서 데이터 자체를 어디에 저장할지는 아직 확정하지 않습니다.

공개 GitHub 저장소는 코드·문서 관리 용도로 사용하고, 개인정보가 포함된 실제 데이터 저장 위치는 보안 요구사항을 먼저 정한 뒤 선택합니다.

---

## 5. 구현 전 확인 순서

1. 비밀키 보관·서명 방식 결정
2. challenge 발급·만료·재사용 방지 정책 정의
3. 인증 성공 후 세션 유지 방식 정의
4. 개인정보 데이터 저장 위치 정의
5. 최소 API 구조 정의
6. Vercel 기준으로 구현 시작

기술 선택은 이 순서에서 필요한 조건이 확인된 뒤 결정합니다.
